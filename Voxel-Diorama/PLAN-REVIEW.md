### 1. [HIGH] cancelled '폐허 없음'과 D9 '기존 폐허 불변'·여행 종료 조건의 상호작용 미정의

- **렌즈**: 내부 일관성 · **위치**: §3.4 표 cancelled 행 ↔ §3.5 종료 조건('done 또는 cancelled') ↔ D9
- **문제**: 거절된 업무는 todo로 돌아가므로, 재작업을 포기한 업무로 여행을 끝내려면 사용자가 cancelled로 보내는 것이 유일한 경로다. 그런데 cancelled 행은 '진행 표식 제거, 폐허 없음'이라, 이미 거절로 생긴 폐허를 지우는지(D9 '기존 폐허 불변' 위반) 신규 폐허만 안 만든다는 뜻인지 두 갈래로 읽힌다. 폐허만 있고 건물 없는 취소 업무의 점수(0점?)와 스냅샷 포함 여부도 미정의라, '폐허 여러 개 + 취소' 업무 처리 시 구현이 갈린다.
- **수정안**: 최소 수정 두 곳: (1) §3.4 표의 cancelled 행을 '진행 표식 제거. 신규 건설·폐허 생성 없음 — 이전 거절로 생긴 폐허는 D9대로 영구 보존'으로 교체. (2) §3.5 종료 조건 항목 뒤에 한 줄 추가: '재작업을 포기한 거절 업무는 사용자가 cancelled로 전환해 여행을 종료할 수 있다. 취소 업무는 점수 0이며, 해당 업무의 폐허는 종료 스냅샷에 포함된다.' 별도 섹션 신설이나 흐름도 추가는 불필요 — 기존 표·목록에 문장 삽입으로 충분하다.
- ☑ 반영 완료 (2026-07-21, PLAN.md)

### 2. [HIGH] 승인 순간이 2D HUD 클릭으로 끝난다 — 보상 연출이 클릭과 연결되어 있지 않음

- **렌즈**: 제품 비전 · **위치**: §3.4 상태 투영 매핑 · §5 연출 · Phase 3
- **문제**: '승인 시 건물 솟는 애니메이션'(§5)은 존재하지만, 승인 행위 자체는 Astryx 리뷰 큐(2D)에서 일어나고 그 클릭이 3D 연출로 이어진다는 명세가 어디에도 없다. 사용자가 HUD만 보고 승인하면 건물은 섬 어딘가에서 조용히 솟고, 원작의 핵심 재미인 '업무를 끝내면 섬에 건물을 놓는다'는 순간이 로그 갱신 수준으로 죽는다. Phase 3 체크포인트도 '폐허 1 + 건물 1' 결과 상태만 검증하고 순간의 경험은 검증하지 않는다.
- **수정안**: §5 연출 항목에 추가: "승인/반려 확정 클릭 시 카메라(D15 이동·줌)가 해당 부지로 자동 이동한 뒤 건물 솟기(승인) 또는 붕괴→폐허(반려) 연출과 점수 카운트업을 재생한다. HUD에서의 확정이 반드시 3D 연출로 이어지며, prefers-reduced-motion 시 카메라 컷 전환+즉시 상태 반영으로 대체." Phase 3 체크포인트에 추가: "승인/반려 클릭이 해당 부지 카메라 이동과 연출로 이어지는 것을 확인." 신규 에셋·의존성 없음 — 기존 D15 카메라와 §5 애니메이션 프리셋의 조합만 명세하는 것.
- ☑ 반영 완료 (2026-07-21, PLAN.md)

### 3. [HIGH] '수정 요청 ≠ 반려' 탈출구가 무제한이라 폐허가 실제로는 생기지 않게 됨

- **렌즈**: 제품 비전 · **위치**: D9 · §3.4 (수정 요청 행)
- **문제**: 반려=영구 폐허의 긴장감이 이 게임의 심장인데, 코멘트 기반 수정 요청은 횟수 제한도 사용 기준도 없다. 1인 사용자는 손실 회피 심리상 폐허를 만들지 않으려고 항상 수정 요청만 쓰게 되고, 결과적으로 섬에는 폐허가 하나도 안 생긴다. '잔해는 영원히 남는다'는 규칙이 서류상으로만 존재하고 실전에서 발동하지 않으면 원작 재미의 절반이 죽는다.
- **수정안**: D9와 §3.3에 경계 규칙 한 줄을 추가: "§3.2의 완료 조건 중 하나라도 미충족인 결과물은 반드시 반려(폐허)로 처리한다. 수정 요청(코멘트)은 완료 조건을 모두 충족한 결과물의 마이너 조정에만 허용한다." §3.4의 '수정 요청' 행 비고에도 "완료 조건 전부 충족 시에만 사용 가능"을 병기. 시도당 수정 요청 횟수 상한(예: 2회 초과 시 승인/반려 강제)은 v0.1에서는 강제 구현 대신 §7 자동 검증 목록에 선택 항목으로만 추가 — 기존 §3.2 완료 조건 필드를 재사용하므로 코드·스키마 변경 없이 규칙 텍스트만으로 해결된다.
- ☑ 반영 완료 (2026-07-21, PLAN.md)

### 4. [HIGH] 첫 실행(여행 없음) 상태가 어디에도 정의되지 않음

- **렌즈**: 1인 범위 · **위치**: §3.4 상태 투영 매핑 · §4.2 GET /api/bootstrap · Phase 2
- **문제**: §1 성공 조건이 '여행을 시작하고'로 시작하지만, 여행이 하나도 없는 최초 실행에서 bootstrap이 무엇을 반환하는지, 화면에 무엇이 뜨는지, 활성 여행 없이 POST /api/tasks를 호출하면 어떻게 되는지가 전부 미정이다. Phase 2 첫 화면 구현에서 즉시 부딪히는 상태인데 매핑 표·API 계약 어디에도 없다. 여행 도중 업무 추가 허용 여부도 §3.5에 명시가 없어 암묵적이다.
- **수정안**: 3줄 수준의 최소 수정으로 충분하다. (1) §3.4 표 위나 아래에 한 줄 추가: "활성 여행 없음 — 3D 장면 없이 행성 로비만 표시, HUD는 '여행 시작' 단일 CTA. 첫 실행도 이 상태다." (2) §4.2 bootstrap 항목을 "활성 여행·업무·직원·캐시 상태 (활성 여행 없으면 trip: null + 보관 목록만 반환)"로 보강하고, POST /api/tasks에 "활성 여행 없으면 409" 한 구절 추가. (3) §3.5에 "여행 도중 최상위 업무 추가는 언제든 가능(종료 조건만 §3.5의 done/cancelled 규칙을 따름)" 한 줄 추가. 별도 온보딩 플로우나 빈 상태 전용 섹션은 만들지 말 것 — 위 세 줄이면 Phase 2 구현 모호성이 해소된다.
- ☑ 반영 완료 (2026-07-21, PLAN.md)

### 5. [HIGH] 반려→재작업 트리거와 수정 요청(코멘트) 경로가 API에 없음

- **렌즈**: 1인 범위 · **위치**: §3.4 매핑 표('수정 요청', '사용자 거절 → todo') · §4.2 브리지 API · §3.3
- **문제**: 매핑 표는 '수정 요청(코멘트) ≠ 반려' 흐름을 약속하지만 브리지 API에는 코멘트 엔드포인트가 없다. 더 치명적으로, 거절 시 피드백이 '에이전트의 다음 시도 입력이 된다'고 했는데 거절→todo 이후 누가/무엇이 재작업을 유발하는지(Paperclip이 자동 재배정하는지, TD 넛지가 필요한지) 미정이다. 이것이 §1 루프 5단계(재작업 승인)의 힌지인데 리스크 표에 '상태명 미실측'으로만 뭉뚱그려져 있다.
- **수정안**: 최소 수정 3곳: (1) §4.2의 `POST /api/tasks/:id/review`를 `decision: approve | reject | request_changes`로 확장하고, request_changes는 Paperclip 코멘트로 전달되며 반려가 아님(D9)을 한 줄로 명시 — 별도 코멘트 엔드포인트는 만들지 않는다. (2) §3.1에 재작업 트리거 규칙 1줄 추가: "거절 피드백 제출 후 에이전트가 자동으로 재시도하지 않으면 TD가 해당 피드백을 인용해 넛지하여 재작업을 시작시킨다 — Phase 1 실사에서 자동 여부 확정." (3) Phase 1 체크포인트에 별도 항목 추가: "거절 피드백 제출 → 에이전트가 실제로 재시도를 시작하는 경로 확인 (자동 재배정인지 TD 넛지 필요인지 기록)." 아울러 §8 리스크 표의 'Paperclip API 계약 미실측' 항목에 '거절→재작업 트리거 경로'를 명시적으로 추가.
- ☑ 반영 완료 (2026-07-21, PLAN.md)

### 6. [HIGH] 잠금 결정 L3의 '국가 = 스프린트 군도' 구조가 소실·모호화됨

- **렌즈**: 통합 충실도 · **위치**: §2 D3 · §6 Phase 4 · §4.5 ThemeManifest
- **문제**: Claude v0.2에서 사용자가 잠근 L3(재논의 없음)는 '행성 → 국가 → 국가 안에 스프린트별 섬 군도(archipelago)'이고, v0.2 시스템 트리 A2에 '국가 뷰: 스프린트 군도'가 별도 장면으로, Gemini Phase 4에도 '지구본 군도 아카이브'로 존재한다. 최종본 D3는 '행성 로비(보관 섬 선택·열람 전용) → 국가 테마 → 여행별 새 섬'으로 국가를 사실상 테마 이름으로 축소했고, Phase 4.3은 행성 로비에서 보관 섬을 직접 선택하게 해 국가 단위 군도 뷰가 존재하는지 여부가 어디에도 없다. §9 백로그에도 없어 잘린 것인지 얼버무린 것인지 판단 불가. 이에 연동된 v0.2 manifest 계약의 anchor(행성 위 국가 위치) 필드도 §4.5 ThemeManifest에서 사라졌다. Phase 4 구현자가 보관 섬 목록 구조(국가별 그룹핑 여부)와 행성 위 국가 마커 표현을 결정할 수 없다.
- **수정안**: 세 줄만 고친다. (1) §2 D3를 다음으로 보강: "행성 로비(보관 섬 선택·열람 전용, 구면 보행 게임 아님) → 국가 테마 → 여행별 새 섬, 과거 섬 영구 보존. **v0.1 로비는 국가 마커 없는 보관 섬 평면 목록** — L3의 '국가별 스프린트 군도 뷰'는 구조 유지하되 v1.1로 시점 이연 (테마가 base 1개뿐인 v0.1에서는 국가 그룹핑이 무의미)". (2) §9 v1.1 후보 4번(KR 테마) 뒤에 추가: "행성 국가 마커 + 국가별 군도 뷰 — 이때 ThemeManifest에 anchor(행성 위 국가 위치) 필드 복원, 국가 2개 이상이 되는 KR 테마와 함께 도입". (3) §6 Phase 4.3에 한 구절 추가: "보관 섬은 평면 목록(국가 그룹핑 없음, v1.1에서 군도 뷰로 확장)". anchor 필드를 v0.1 §4.5에 미리 넣는 것은 하지 않는다 — 사용처가 없는 스키마 필드는 YAGNI.
- ☑ 반영 완료 (2026-07-21, 권장안 채택 — 사용자 확인)

### 7. [HIGH] Astryx는 React >=19 필수 → R3F v9 강제인데 계획에 버전 제약이 전혀 없음

- **렌즈**: 기술 타당성 · **위치**: §4.1 구조 원칙 · §2 D13 인접 (스택 정의 전반)
- **문제**: facebook/astryx packages/core의 peerDependencies는 react >=19.0.0, react-dom >=19.0.0, @stylexjs/stylex ^0.19.0이다. 한편 @react-three/fiber는 v8=React 18, v9=React 19로 짝이 고정되어 있다(공식 v9 마이그레이션 가이드). 즉 이 스택은 React 19 + R3F v9로만 성립하는데, 계획서 어디에도 React·R3F 버전이 없다. React 18 + R3F v8로 시작하면 Astryx 설치 시점(Phase 2)에 peer dependency 충돌로 막힌다. 또한 @stylexjs/stylex가 peer dep이므로(README의 'no build plugin' 문구는 빌드 플러그인 불요라는 뜻이지 패키지 불요가 아님) pnpm 사용 시 자동 설치되지 않아 명시 설치가 필요하다.
- **수정안**: §4.1 구조 원칙에 버전 기준선 한 줄 추가: "스택 버전 기준선 — React 19 + react-dom 19, @react-three/fiber v9(+@react-three/drei v10 계열), @astryxdesign/core는 특정 버전으로 pin(예: package.json에 정확 버전 고정, 캐럿 금지), @stylexjs/stylex ^0.19는 peer dependency이므로 pnpm에서 명시 설치". 기존 "버전 고정" 문구는 이 구체 pin을 가리키도록 갱신. 아울러 §6 Phase 2 체크포인트에 "Astryx HUD와 R3F Canvas를 동일 앱에서 함께 렌더해 peer dependency 충돌 없음 및 공존 렌더를 1회 실증" 항목 추가. §7 리스크 표의 "Astryx beta API 변동" 행 완화책에 "React 19/R3F v9 강결합"을 명시해 스택 교체 시 연쇄 영향을 기록.
- ☑ 반영 완료 (2026-07-21, PLAN.md)

### 8. [MEDIUM] Phase 2~3이 여행(Phase 4) 없이 최상위 업무·섬·점수를 구현 — 의존성 역전

- **렌즈**: 내부 일관성 · **위치**: §6 Phase 2·3 ↔ §3.5(여행 루트 업무 하위 배치), §3.1(최상위 = 여행 루트 바로 아래), D3(섬 = 여행별)
- **문제**: §3.1은 건물·점수 대상인 '최상위 업무'를 '여행 루트 바로 아래'로 정의하고, D3·§3.5는 섬을 여행 단위로 생성한다. 그런데 여행 시작·종료는 Phase 4에서야 도입되고, Phase 2는 업무 생성·검수, Phase 3은 섬·건물·폐허·점수를 먼저 구현한다. 여행 루트가 없는 Phase 2~3에서는 '최상위 업무' 판정 기준과 Phase 3 섬이 소속될 여행이 정의되지 않아, 비용·점수 중복 방지 규칙(§3.1)도 적용 근거를 잃는다.
