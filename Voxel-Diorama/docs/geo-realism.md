# 지오-리얼리즘 — 실제 지도(OSM)로 섬 지형을 만든다

> **상태**: 연구·설계안 (2026-07-27). 아직 결정 아님 — §5의 D 결정 개정은 **인간 승인 필요**(D4).
> **원천**: `little-city/little-taipei/plans/realism-plan.md` (craftmygame/little-city) 및 그 `scripts/` 3종을 실사 분석.
> 함께 본 것: `tiny-world-builder`(LandscapeEngine), `mykonos-island-voxels`(그리드 배치), `animal-island-ui`.

---

## 0. 한 문장

little-taipei가 증명한 것은 "예쁜 도시"가 아니라 **지도의 정확도를 기계가 판정할 수 있게 만든 구조**다. 우리가 훔칠 것은 도시가 아니라 그 구조다.

---

## 1. 왜 이게 우리에게 중요한가 (도그푸딩 관점)

우리 v0.1의 미해결 난제 하나: **3D 레이아웃 업무를 인간이 어떻게 검수하는가.** 지금은 QA가 스크린샷을 찍고 "괜찮아 보인다"고 쓴다 — §3.2 "검증 가능한 완료 조건"의 가장 약한 고리다.

little-taipei는 이걸 두 개의 산출물로 해결했다:

1. `npm run check` → **좌표 드리프트 리포트**. 존별 허용치(0.15 / 0.4 km) 초과 시 **빌드 실패**. 판정이 의견이 아니라 종료 코드가 된다.
2. `map-preview.mjs` → **게임 데이터(회색) vs OSM 정답(마젠타) 겹쳐 그린 SVG**. 사용자가 올린 이미지 01~04가 정확히 이 산출물이다.

에이전트는 눈이 없다. **눈이 없는 노동자에게 지도를 맡기려면 이 두 개가 선행 조건이다.** 이게 이 문서의 핵심 주장이다.

## 2. 이식 가능한 원리 7가지

### 2-1. 데이터는 진짜 km, 왜곡은 런타임 변환 한 곳에만 (가장 중요)

little-taipei는 Phase 2에서 도시 데이터를 전부 "타이베이101 기준 진짜 km"로 정규화하고, 디오라마 특유의 압축·팽창을 **전부** `planet.spread` 하나로 몰았다.

```
authored data (true km)  ──spread()──▶  rendered position
        ▲                                      ▲
   OSM으로 검증 가능                      "귀엽게" 튜닝 가능
```

왜 결정적인가: 데이터에 왜곡이 섞여 있으면 **외부 정답과 대조가 불가능**해진다. 그들의 원래 데이터는 신이 코어가 ×2 미리 부풀려져 있었고(City Hall ×2.58, Hyatt ×4.08 — 개별적으로 제각각), 그래서 "지도가 맞나"라는 질문 자체에 답할 수 없었다.

> **우리 적용**: 섬 좌표는 테마 앵커 기준 진짜 km. 디오라마 압축(작은 섬·촘촘한 부지)은 R3F 레이어의 `spread()` 하나. **D8의 나선은 이 변환 이전 좌표계에서 정의한다.**

### 2-2. 불변식은 "방위 + 위상"이지 "거리"가 아니다

- A가 B의 북동쪽이면 게임에서도 북동쪽 (방위)
- 도로 교차 순서, 강의 어느 쪽 — 유지 (위상)
- **절대 거리는 일치하면 안 된다. 압축은 의도다.**

디오라마에 정확히 맞는 타협이다. 우리는 "축소 모형"을 만드는 것이지 축척 지도를 만드는 게 아니다.

### 2-3. 충실도 존 — 노력 예산을 나눈다

| 존 | 대상 | 허용 드리프트 | 작업 |
|---|---|---|---|
| A | 시그니처 랜드마크 13개 | 0.15 km | 실좌표 + 인지 루브릭 + 내부 |
| A-lite | 2군 랜드마크 5개 | 0.4 km | 외관 인지만 |
| B | 간선도로·강·다리 전체 | 0.4 km | 위상만, 건물 없음 |
| C | 배경 산맥 | **방위 ≤10°만** | 방향·덩어리감만 |

존 C가 거리 대신 **각도**로 검사된다는 게 영리하다 — 행성 둘레가 유한하니 먼 산은 거리를 포기하고 방위만 지킨다.

> 위 표는 **little-taipei의 존**이다. 우리 것은 아래가 확정판이다.

#### 우리 존 — v0.1 확정 (2026-07-28, G1 승인과 함께)

| 존 | 대상 | 허용 드리프트 | 교토 실적 |
|---|---|---|---|
| A | 랜드마크 (점 피처) | 0.15 km | 33건 |
| B | 도로 (선 피처) | 0.4 km | 22건 |
| C | 강 (선 피처) | 1.5 km | 8건 |

`tools/geo/check-geo.mjs`가 이 값을 강제한다(위반 1건이면 exit 1). **little-taipei와 두 군데 다르다**:

1. **C를 각도가 아니라 거리로 잰다.** 원본의 존 C는 배경 산맥이라 방위 ≤10°가 맞지만, 우리 C는 강이다. 강은 섬 안에 실물로 놓이므로 거리로 재는 게 맞고, 긴 선형이라 허용치를 크게(1.5 km) 준다. 배경 산맥을 넣게 되면 그때 각도 존을 따로 만든다 — 지금 만들면 YAGNI다.
2. **A-lite를 두지 않는다.** 랜드마크가 33건뿐이라 2군을 나눌 실익이 없다. 섬당 랜드마크가 50건을 넘으면 그때 쪼갠다.

> **테마 섬당 목표**: Zone A 5~8개(그 도시를 알아보게 하는 최소 집합)면 충분하다. 교토 33건은 정답 데이터의 전량이지 섬에 다 세운다는 뜻이 아니다.

### 2-4. 정답은 스크립트로 가져온다 — 수작업 좌표 조사 금지

`fetch-geo-truth.mjs` → Overpass API 질의 → `geo-truth.json`(73개 피처) **커밋**. 재실행 가능, ODbL 오픈 라이선스.

```json
{"source":"OpenStreetMap via Overpass API (ODbL)",
 "origin":{"lat":25.0337,"lon":121.5645},
 "features":[{"id":"taipei-101","kind":"point","zone":"A","at":[-0.004,0.021],
              "osmName":"台北101","osmType":"way/248210267"}, ...]}
```

사용자가 말한 **"73개의 도로·강·랜드마크"가 바로 이 `features` 배열**이다(실측: 정확히 73개).

투영은 단순 등거리 원통(정답 원점 주변 소영역이라 충분):
```js
const KM_LAT = 110.574, KM_LON = 111.320 * Math.cos(LAT0 * Math.PI/180);
proj = (lat,lon) => [(lon-LON0)*KM_LON, (lat-LAT0)*KM_LAT];  // [east, north] km
```

### 2-5. 검수 산출물 = 겹쳐 그린 SVG

`map-preview.mjs`: 의존성 0, 게임 데이터와 OSM 정답을 한 장에. **3 프레이밍 × 2 모드 = 6장**.

- 프레이밍: `basin`(±12km) / `grid`(±6km) / `xinyi`(±2km) — 광역·도시·코어
- 모드: `raw`(저작 좌표 그대로) / `spread`(런타임 변환 통과)
- 런타임 변환은 **main.js에서 그대로 복사**해 넣는다 — 툴과 게임이 갈라지면 툴이 거짓말을 한다

사용자 이미지 판독:
- **01 `grid/raw`** — 회색(게임)과 마젠타(OSM)가 크게 어긋남 → 저작 좌표가 아직 부풀려진 상태. **버그가 아니라 Phase 1이 드러내야 할 것**
- **02 `grid/spread`** — 변환 통과 후 두 층이 거의 겹침 → 정규화 성공의 증거
- **03 `xinyi/spread`** — 코어 확대, 개별 랜드마크 단위 대조
- **04 `basin/spread`** — 광역, 강 3개와 산맥 링까지

> **우리 적용**: 이 SVG를 **검수 첨부물의 표준 포맷**으로 채택. 인간이 게임을 띄우지 않고도 배치 업무를 판정할 수 있게 된다 — §3.2 완료 조건의 약한 고리를 메운다.

### 2-6. 건물 기준은 "인지 루브릭"이지 사진 재현이 아니다

실루엣 + 지배 색상 + 시그니처 특징 2~3개. 복셀 양식에 정확히 맞고, **에이전트가 체크리스트로 판정 가능**하다.

### 2-7. 그들이 밤새 얻은 실패 데이터 (공짜로 가져올 것)

`realism-plan.md`의 "Overnight run log"는 값이 비싼 부분이다:

| 겪은 일 | 교훈 |
|---|---|
| 피처별 Overpass 질의 → **레이트 리밋 + 45초 타임아웃** | **대량 질의 3~4개 + 로컬 매칭**으로 전환. 필수 |
| 타 지역 동명 도로(信義路가 신뎬에도 있음) | 매니페스트에 **피처별 bbox** |
| 도로 폴리라인이 과다 | **Douglas-Peucker로 도로 ≤8점, 강 ≤10점** |
| 강을 OSM 중심선으로 교체 | **손저작 오류 2건이 드러남**(담수강 1.7km 서편, 지룽강 진입 방위가 반대) — 정답 도입은 미관이 아니라 버그 수정 |
| 정규화하면서 기존 렌더 완전 보존 시도 | **수학적으로 불가능**했다(옛 데이터가 한 반경을 이중 점유). 작은 이동은 수용, **위상 변화는 불가**로 선을 그음 |
| 강을 실제 위치로 옮기니 과장된 폭이 동네를 침수 | 폭 **0.62 → 0.30 km**. 정확도와 스타일 파라미터는 커플링돼 있다 |
| 도로 하나가 OSM에서 0.2km 스텁으로 옴 | 자동 수집은 **쓰레기도 가져온다**. 스킵하되 정답에는 남김 |

## 3. 우리 맵에 어떻게 적용하는가

### 3-1. 큰 그림 — 섬은 추상 격자가 아니라 "압축된 실제 도시"

현재: 섬 = 빈 지면 + 중앙에서 바깥으로 도는 나선 부지.
제안: 섬 = **그 테마 도시의 간선 도로망·강·해안선** + 그 위의 부지.

AI 업무가 건물이 된다는 컨셉이 훨씬 강해진다 — 내 업무들이 **교토의 실제 거리에** 쌓인다.

### 3-2. D8과 충돌하지 않게 만드는 방법 (핵심)

D8: *"부지 = 섬 중앙→바깥 결정적 나선"*. VOX-25가 방금 이걸 구현했다.

**교체 대상은 함수 하나뿐이다.**

```
지금:  slot(n) → spiral(n)                       // 빈 평면의 n번째 나선 칸
제안:  slot(n) → PLOTS[n]                        // 미리 계산된 도시 부지 목록의 n번째
       PLOTS = 도로망에서 유도한 블록 내부 부지를
               (앵커로부터의 거리, 그다음 각도) 로 결정적 정렬
```

- 결정론 **유지** (해시·순서 규칙 그대로)
- "중앙→바깥" 의미 **유지** (정렬 1순위가 앵커 거리)
- VOX-25 산출물 **보존** — 슬롯 생성기만 갈아끼움

> ⚠️ 그래도 D8 문구("나선")는 개정이 필요하다. **D 결정 개정은 인간 전용(D4)** — §5.

### 3-3. 데이터 스키마 (little-taipei 스키마를 축약)

```js
// themes/<themeId>/city.js — 좌표는 앵커 기준 진짜 km [east, north]
export const CITY = {
  id: 'jp-kyoto', anchor: { lat: 34.9858, lon: 135.7588 },  // 京都駅
  planet: { unitsPerKm, spread: { /* 압축 파라미터 — 여기에만 왜곡 */ } },
  roads:     [{ id, name, widthKm, path: [[e,n], ...] }],   // ≤8점
  waterways: [{ id, name, halfWidthKm, path: [...] }],      // ≤10점
  landmarks: [{ id, name, at: [e,n], zone: 'A' }],          // 배치 앵커 겸 랜드마크
};
```

`placement`(cols/foot/claim 등)는 little-taipei가 걸어보는 게임이라 필요한 것 — **우리는 D15 고정 아이소메트릭이라 불필요**. 가져오지 않는다.

### 3-4. 도구 3종 (이식판)

| 스크립트 | 하는 일 | 우리 쪽 변경 |
|---|---|---|
| `scripts/fetch-geo-truth.mjs` | Overpass 대량 질의 → `geo-truth.json` | 매니페스트를 테마별로. 엔드포인트 다중화 + 백오프 **필수**(§4) |
| `scripts/check-city.mjs` | 존별 드리프트, strict 시 실패 | 그대로. `npm run check`에 물림 |
| `scripts/map-preview.mjs` | 대조 SVG 6장 | 프레이밍 이름만 우리 테마에 맞게 |

셋 다 **의존성 0, 앱 코드 미접촉**. 지금 발주해도 실행 중인 앱에 위험이 없다 — 이게 조기 착수를 정당화한다.

## 4. 실사로 확인한 위험

- **Overpass 가용성이 실제 병목이다.** 오늘(2026-07-27) 교토 프로브를 직접 쳐본 결과:
  - `overpass-api.de`, 클라이언트 타임아웃 50초 → **HTTP 504** "server is probably too busy"
  - `overpass.kumi.systems`, 60초 → 무응답
  - `overpass-api.de`, **타임아웃 110초 / 질의 timeout 100 → 성공** (京都タワー node/1494857741 @ 34.98755, 135.75933)
  → 즉 **되긴 되는데 느리다.** fetch 스크립트는 **엔드포인트 다중화 + 재시도 4회 + 긴 타임아웃(≥100초) + 원시 응답 캐시**가 선택이 아니라 필수다. little-taipei가 이미 그렇게 짜여 있다(ENDPOINTS 배열 + 4회 루프 + `clientTimeout` 100초 기본). 그대로 가져온다.
- **라이선스**: OSM 파생 데이터는 **ODbL**. `geo-truth.json`에 `source` 필드로 명시하고 `THIRD_PARTY.md`에 등재해야 한다. (little-taipei가 이미 그 형식.)
- **비결정성 유입**: OSM은 시간이 지나면 바뀐다. 정답 JSON을 **커밋**해서 재실행 없이도 빌드가 재현되게 한다 (그들이 그렇게 함).
- **범위 팽창**: 이건 큰 기능이다. v0.1은 아직 Phase 3다. §5 참고.

## 7. 안 가져오는 것 (YAGNI)

- **걸어다니는 게임 요소** — 콜라이더(`cols`), 내부 공간, 스폰 시선축, 다리 갑판 아래 통과. 우리는 D15 고정 아이소메트릭.
- **타이베이101 전망대 히어로 연출** — 훌륭하지만 우리 컨셉과 무관.
- **행성 대척점 폐합 모델** — 우리 로비 행성은 열람 전용(D3)이라 구면 보행이 없다.
- **18개 랜드마크 병렬 감사** — v0.1엔 5~8개면 충분.
- `tiny-world-builder`의 `LandscapeEngine`(1600줄 절차 지형·바이옴 스트리밍) — 우리 섬은 작고 고정이다. 참고만.
